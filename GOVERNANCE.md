# Governance

Agent-Safe Pipeline is maintained as the public reference implementation for an execution boundary
where agents may propose actions but cannot authorize their own execution. Governance decisions
must preserve that boundary, the Apache-2.0 license, and truthful public evidence.

## Roles and current maintainers

The following access snapshot is current as of 2026-08-17:

- **Project lead and code owner — [@ocularminds](https://github.com/ocularminds):** final authority
  for product scope, trust-boundary changes, releases, maintainer appointments, repository settings,
  npm trusted-publisher configuration, and emergency recovery.
- **Maintainer — [@yunaremaia](https://github.com/yunaremaia):** has the GitHub `maintain` role and
  may triage issues, review changes, manage ordinary repository work, and prepare release or
  security remediations. This role does not currently include the code-owner bypass, npm
  organization recovery, or unilateral release authority.
- **Contributor:** may propose issues and pull requests and participate in review. A contributor
  does not gain execution, release, secret, or policy authority through authorship.
- **Security responder:** receives the minimum private access needed to triage an advisory. The
  assignment is incident-specific and does not imply general maintainer or release authority.

The checked-in `CODEOWNERS` file and active `master` ruleset are the enforceable source for review
authority. GitHub and npm settings remain external controls; this document must be updated in the
same change whenever those roles materially change.

## Decision process

Routine changes proceed by pull request after required checks and code-owner review pass. Reviewers
check scope, tests, security and failure behavior, documentation claims, licensing, and whether the
change preserves independent authorization.

Trust-boundary, security-policy, release, dependency-exception, governance, and maintainer-access
changes require explicit project-lead approval. Material disagreements are recorded in a public
issue or pull request with the alternatives and decision rationale, except when coordinated
disclosure requires a private advisory. No maintainer may approve their own access expansion or
adjudicate a conduct report in which they are involved.

## Adding and removing maintainers

A maintainer candidate is nominated through a public issue or pull request after sustained,
constructive contributions. The project lead evaluates technical judgment, security-boundary
understanding, review quality, code-of-conduct history, availability, and conflicts of interest.
Access is granted at the least-privileged role needed. The appointment, decision authority,
`CODEOWNERS`, rulesets, and this roster are updated together when applicable.

A maintainer may step down at any time. Access may also be suspended or removed for compromised
credentials, an unresolved conflict of interest, loss of trust, or a serious code-of-conduct or
security-policy violation. Inactivity alone does not silently remove a maintainer: the project lead
first attempts contact and records the resulting roster change. Emergency access removal may occur
before the public record when disclosure would increase risk.

## Contribution sign-off

Human contributions use the [Developer Certificate of Origin](https://developercertificate.org/),
not a contributor license agreement. Every pull-request commit must contain an author-matching
trailer:

```text
Signed-off-by: Contributor Name <contributor@example.com>
```

`git commit -s` adds the trailer. The `DCO` workflow checks at most 500 commits from the exact pull
request base and head SHAs and fails if a commit lacks a trailer matching its Git author name and
email. An exact GitHub-authenticated Dependabot commit on a Dependabot-authored pull request is
exempt because it is generated by the repository's configured dependency service. Human-authored
changes are not exempt. Required-review and CI controls still apply to all bot changes.

## Access continuity and bus factor

The repository has two people with project roles, public source and operational documentation,
protected pull requests, keyless npm publication, and independently verifiable releases. These
controls reduce recovery knowledge and credential concentration.

They do not yet establish a bus factor of two. `@ocularminds` remains the sole code owner,
ruleset-recovery principal, npm organization recovery authority, and final release authority. If
the project lead becomes unavailable, the maintainer can triage, review, and prepare changes but
cannot complete every protected recovery or publication action independently. The OpenSSF
`access_continuity` and `bus_factor` answers therefore remain **Unmet**, with this section as the
public justification.

Those answers may change only after a second person has least-privilege access to private security
reports, code-owner or protected-branch recovery, npm organization recovery, and emergency release
operations, and has completed a documented recovery exercise. Expanding access merely to improve a
badge score is not sufficient.
